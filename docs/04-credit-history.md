# Кредитная история: откуда берём, как обрабатываем и где храним

## Схема потока

```
Клиент/андеррайтер -> POST /api/applications/:id/credit-history/refresh
        -> CreditHistoryService
             -> BkiMockService (синтетический источник по ИНН)
             -> CreditReport (БД) + ExternalCheck (БД)
             -> AuditLog
        <- нормализованный отчёт + checkStatus + flags
Скоринг -> CreditHistoryService.getForApplication -> CreditReport (последний по заявке)
Фронтенд -> только GET-эндпоинты, прямого доступа к источнику нет
```

## Источник данных

Внешний источник подменён моком — требование кейса: только синтетические данные, без платных API.

`backend/src/modules/mocks/bki-mock.service.ts`:

- брокер `BKI-MOCK`;
- профиль выбирается по ИНН компании, для неизвестных ИНН — детерминированный fallback от суммы кодов символов;
- отдаёт: скоринг бюро, вклад в кредитную историю, просрочки, общий долг, ежемесячный платёж, открытые/закрытые кредиты, признаки банкротства и ликвидации.

Профили демо-сценариев:

| ИНН | Компания | Скоринг | Просрочка | Банкротство | Ожидаемый исход |
| --- | --- | --- | --- | --- | --- |
| `7701234567` | ООО «Восход» | 780 | 0 дн. | нет | одобрение |
| `7709876543` | ИП Орлов П. С. | 645 | 18 дн., 47 000 ₽ | нет | контрпредложение |
| `7705554433` | ООО «Северторг» | 515 | 124 дн., 350 000 ₽ | да | отказ |

## Эндпоинты

| Метод | Путь | Роль | Что делает |
| --- | --- | --- | --- |
| `POST` | `/api/applications/:id/credit-history/refresh` | банк | запрашивает отчёт у мока и сохраняет новый снимок |
| `GET` | `/api/applications/:id/credit-history` | владелец / банк | последний отчёт по заявке |
| `GET` | `/api/companies/:companyId/credit-history` | банк, клиент своей компании | последний отчёт по компании |
| `GET` | `/api/mock/bki/:companyId` | банк | сырой ответ мока для отладки |

`refresh` возвращает `{ report, checkStatus, flags }`, где:

- `checkStatus`: `PASSED` (без просрочек), `WARNING` (есть просрочка), `FAILED` (банкротство);
- `flags`: `BANKRUPTCY`, `HAS_OVERDUE`, `REGISTRY_NOT_VERIFIED`.

## Что сохраняется

`CreditReport` (снимок на момент запроса, история снимков не перезаписывается):

| Поле | Смысл |
| --- | --- |
| `companyId`, `applicationId` | к кому относится отчёт |
| `bureau` | `BKI-MOCK` |
| `creditScore` | скоринг бюро (0..1000) |
| `historyScore` | вклад фактора «качество истории» (0..25) |
| `overdueDays`, `overdueAmount` | просрочка |
| `totalDebt`, `monthlyDebtPayment` | долг и платёж |
| `openLoans`, `closedLoans` | кредиты |
| `hasBankruptcy`, `isLiquidated`, `registryVerified` | стоп-факторы |
| `rawPayload` | исходный JSON мока для воспроизводимости |

Дополнительно пишется `ExternalCheck` (источник `BKI`, статус `PASSED/WARNING/FAILED`, payload) и запись в `AuditLog` с действием `CREDIT_HISTORY_REFRESHED`.

## Как это использует скоринг

`ScoringService.run` берёт последний отчёт по заявке и передаёт в провайдер:

- `historyScore` → фактор «Качество кредитной истории» (вес 25);
- `monthlyDebtPayment` → фактор «Долговая нагрузка» (вес 20);
- просрочки и банкротство попадают в объяснение фактора и влияют на итоговый балл.

Если отчёта ещё нет, скоринг работает, но помечает оценку как предварительную (`historyScore` отсутствует → 60% веса).

## Политика доступа и хранения

- Сырые данные источника доступны только роли `UNDERWRITER`/`ADMIN`; клиенту отдаётся отчёт по его заявке без `rawPayload`.
- Каждый запрос к источнику фиксируется в `ExternalCheck` и `AuditLog` — видно, кто и когда запрашивал.
- Снимки не удаляются при пересчёте: можно показать, на каких данных принималось решение.
- Персональные данные клиента в отчёт не попадают — только агрегаты по компании.
- На проде: заменить `BkiMockService` на клиент реального БКИ, сохранить контракт `BureauReport`, добавить таймауты, ретраи и шифрование `rawPayload`.
