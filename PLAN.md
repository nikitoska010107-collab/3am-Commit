# План проекта: «Умный кредитный кабинет предпринимателя»

Кейс: Alfa Hack 2026 совместно с АО «Альфа-Банк» (Changellenge).
Документ: рабочая версия плана команды. Срок — **4 рабочих дня**, старт завтра.

---

## 1. Контекст и цель

### 1.1. Что требуется по кейсу

Создать прототип цифрового кредитного конвейера для малого и микробизнеса, который объединяет:

1. **Клиентский путь** — от потребности в финансировании до результата по заявке.
2. **Внутреннюю обработку заявки в банке** — движение заявки, проверки, оценка риска, решение.
3. **Единый работающий процесс** — данные сохраняются, статусы меняются последовательно, система реагирует на действия пользователя.

Целевая аудитория: собственник, гендиректор, финдиректор/бухгалтер, сотрудник, отвечающий за финансирование. Пользователь может **не обладать банковской экспертизой** — интерфейс должен объяснять варианты, статус и следующие шаги.

### 1.2. Что оценивает жюри

| Критерий | Что это значит на практике |
|---|---|
| Целостность решения | Сквозной процесс от обращения до результата, а не набор экранов |
| Качество UX | Понятно клиенту и сотруднику банка на каждом этапе |
| Согласованность модулей | Данные сохраняются и переиспользуются, статусы последовательны |
| Enterprise-ориентированность | Безопасность, надёжность, масштабируемость, сопровождаемость |
| Потенциал развития | Объяснены решения, ограничения и дальнейшие шаги |
| Готовность к проверке | Запускается по инструкции, есть тестовые данные и сценарий |

Дополнительные функции и ИИ приветствуются, **но не заменяют** работоспособность основного сценария.

### 1.3. Жёсткие ограничения кейса

- **Только веб**; мобильное приложение не допускается.
- **Нельзя** обращаться к корпоративным системам Альфа-Банка — только локальные моки/стабы/симуляторы.
- **Только синтетические данные** (клиенты, компании, документы, заявки, финансы).
- **Никаких платных ресурсов** в проверяемой версии: подписок, платных API, покупных данных, закрытых лицензий.
- **LLM — только с открытыми весами** (например, Qwen, Llama через Ollama). Внешние API вроде OpenAI/Anthropic не подходят.
- E-mail, мессенджеры, звонки и SMS **не должны быть частью сценария** — всё внутри продукта.
- Обязателен **Docker** и воспроизводимый запуск на обычном ПК.
- Код в **GitHub** с историей коммитов; нужен commit hash/тег на момент дедлайна. Приватный репозиторий — доступ аккаунту `alfa-hack-2026`.

### 2.1. Ключевой риск состава

В команде нет выделенного бэкендера. Решение: **Влад берёт backend**, потому что он всё равно отвечает за скоринг и данные. Фронтенд и бэкенд разрабатываются параллельно на контракте и моках.

### 2.2. Правила взаимодействия

- Контракт (OpenAPI) — единственный источник правды.
- Фронт не ждёт бэк: MSW-моки по контракту.
- Бэк не ждёт финальный UI: фикстуры и простые схемы.
- Изменение контракта — сразу в общий чат.
- Ежедневно: 15 минут утром (план) и 5 минут вечером (статус).

## 3. Границы MVP

### 3.1. Входит в MVP

1. Вход по тестовым аккаунтам (без регистрации).
2. Каталог из 3 кредитных продуктов с описанием условий.
3. Форма заявки с валидацией и сохранением черновика.
4. Отправка заявки и последовательная смена статусов.
5. Кабинет банка: очередь заявок, карточка, скоринг с факторами.
6. Четыре решения банка: одобрить, отказ, контрпредложение, запросить данные.
7. Ответ клиента на запрос данных и принятие контрпредложения.
8. Аудит-лог переходов.
9. Postgres + сид-данные, переживающие перезапуск.
10. Docker Compose, README, OpenAPI, диаграммы, тестовые сценарии.

### 3.2. Не входит в MVP (в `BACKLOG.md`)

- LLM-ассистент (только если всё готово к вечеру Дня 3).
- OCR и разбор загруженных документов.
- ML-модель скоринга (используем rule-based).
- Реальная подпись и выдача денег.
- Регистрация, восстановление пароля, 2FA.
- Интеграции с реальными БКИ/ЕГРЮЛ/ФНС (только моки).
- Мобильная версия как отдельный продукт.
- Аналитика, админка, экспорт отчётов.
- CI/CD сверх базового линта и тестов.

### 3.3. Допустимые упрощения

- Скоринг — балльная модель, явно описанная в README.
- Подписание — кнопка «Подписать» без реальной криптографии.
- Выдача — смена статуса `DISBURSED` без денежных операций.
- Внешние проверки — синхронные моки с фиксированными ответами.
- Аутентификация — фиктивный JWT по выбранному тестовому пользователю.

## 5. Сквозной демо-сценарий

1. Клиент входит под тестовым аккаунтом.
2. Видит каталог и подсказку, какой продукт подходит под его задачу.
3. Выбирает продукт, заполняет заявку (сумма, срок, цель, данные компании).
4. Отправляет — статус `SUBMITTED`.
5. Андеррайтер открывает заявку в очереди, видит данные и скоринг.
6. Для клиента A: одобрение → клиент принимает → подпись → `DISBURSED`.
7. Для клиента B: контрпредложение (меньше сумма/дольше срок) → клиент принимает.
8. Для клиента C: запрос доп. данных → клиент отвечает → отказ с объяснением.
9. В карточке виден аудит-лог всех переходов.

Демо должно быть **детерминированным**: три заранее засеянных клиента дают три разных исхода.

## 6. Модель состояний заявки

| Статус | Смысл | Кто переводит |
|---|---|---|
| `DRAFT` | Черновик, можно редактировать | Клиент |
| `SUBMITTED` | Отправлена, ждёт проверки | Система |
| `CHECKING` | Валидация и обогащение данными | Система |
| `UNDER_REVIEW` | Скоринг и рассмотрение | Система / андеррайтер |
| `INFO_REQUESTED` | Нужны дополнительные данные | Андеррайтер |
| `APPROVED` | Одобрено на запрошенных условиях | Система / андеррайтер |
| `COUNTER_OFFER` | Одобрено на изменённых условиях | Система / андеррайтер |
| `REJECTED` | Отказ с причинами | Система / андеррайтер |
| `OFFER_ACCEPTED` | Клиент принял условия | Клиент |
| `DOCS_SIGNED` | Документы подписаны (симуляция) | Клиент |
| `DISBURSED` | Средства предоставлены (симуляция) | Система |
| `CANCELLED` | Отозвана клиентом | Клиент |

### 6.1. Разрешённые переходы

```text
DRAFT          -> SUBMITTED
DRAFT          -> CANCELLED
SUBMITTED      -> CHECKING
CHECKING       -> UNDER_REVIEW        (данные полные)
CHECKING       -> INFO_REQUESTED      (не хватает данных)
INFO_REQUESTED -> UNDER_REVIEW        (клиент дополнил)
UNDER_REVIEW   -> APPROVED
UNDER_REVIEW   -> COUNTER_OFFER
UNDER_REVIEW   -> REJECTED
UNDER_REVIEW   -> INFO_REQUESTED
APPROVED       -> OFFER_ACCEPTED      (клиент)
COUNTER_OFFER  -> OFFER_ACCEPTED      (клиент)
COUNTER_OFFER  -> CANCELLED           (клиент отказался)
OFFER_ACCEPTED -> DOCS_SIGNED
DOCS_SIGNED    -> DISBURSED
```

Правило: переход, не описанный в таблице, возвращает `409 Conflict`. Каждый переход пишется в `application_status_history` и `audit_log`.

## 7. Кредитная логика

### 7.1. Принцип

Скоринг и кредитное решение — **разные слои**. Скоринг даёт оценку риска, decision-слой с учётом продукта, суммы, срока и правил банка выбирает исход.

### 7.2. Факторы скоринга (0–100)

| Фактор | Вес | Логика |
|---|---|---|
| Качество кредитной истории | 25 | Просрочки снижают, чистый график повышает |
| Долговая нагрузка | 20 | Отношение платежей к выручке |
| Стабильность выручки | 20 | Динамика за 6–12 месяцев |
| Возраст бизнеса | 15 | Меньше 6 месяцев — низкий балл |
| Отношение суммы к выручке | 10 | Слишком крупная сумма — риск |
| Отраслевой риск | 10 | Справочник отраслей |

### 7.3. Жёсткие стопы

- Действующая просрочка → отказ.
- Банкротство / ликвидация → отказ.
- Не подтверждён статус ЕГРЮЛ/ЕГРИП → запрос данных или отказ.
- Несовпадение данных заявки и компании → запрос данных.

### 7.4. Решение

| Итог | Условие |
|---|---|
| `APPROVED` | Балл ≥ 70 и нет стопов, сумма в лимитах продукта |
| `COUNTER_OFFER` | Балл 45–69 или сумма/срок вне лимитов — предлагаем скорректированные параметры |
| `REJECTED` | Балл < 45 или сработал жёсткий стоп |
| `INFO_REQUESTED` | Не хватает обязательных данных |

Ответ скоринга обязан содержать **объяснение по каждому фактору** (значение, вклад, человекочитаемая причина) — это ключевое для UX и демо.

## 8. Архитектура и стек

### 8.1. Компоненты

```text
[React SPA] --HTTP/JSON--> [FastAPI] --SQL--> [PostgreSQL]
                              |
                              +--> [Scoring service]
                              +--> [Decision service]
                              +--> [Mock BKI]
                              +--> [Mock EGRUL/FNS]
                              +--> [Audit logger]
```

Всё в Docker Compose. Внешние источники — отдельные модули/сервисы с OpenAPI-контрактами.

### 8.2. Стек

- **Frontend:** React 18 + TypeScript + Vite, Tailwind CSS, shadcn/ui, TanStack Query, react-hook-form + zod, React Router.
- **Моки фронта:** MSW (только на время разработки).
- **Backend:** Python 3.12, FastAPI, SQLAlchemy 2, Pydantic 2, Uvicorn.
- **БД:** PostgreSQL 16.
- **Тесты:** pytest (backend), Vitest (frontend), Playwright (один e2e).
- **Инфра:** Docker Compose, GitHub Actions (lint + tests).
- **Деплой:** frontend на Vercel/Netlify, backend на Render/Railway, БД на Neon (бесплатные тиры). Docker Compose остаётся основным способом проверки.

### 8.3. Принципы для «enterprise»-критерия

- Слои: `api` → `services` → `repositories` → `models`.
- Схемы запросов/ответов отделены от ORM-моделей.
- Все переходы статусов — в одном сервисе, а не по роутерам.
- Аудит неизменяем (append-only).
- Секреты — только через переменные окружения, `.env.example` в репозитории.
- Ошибки — единый формат `{code, message, details}`.

## 10. Черновик API

```text
POST   /auth/login
GET    /auth/me

GET    /products
GET    /products/{id}

POST   /applications                    создать черновик
GET    /applications                    список (клиент — свои, банк — все, фильтры)
GET    /applications/{id}
PATCH  /applications/{id}               редактировать черновик
POST   /applications/{id}/submit
POST   /applications/{id}/cancel

POST   /applications/{id}/info-response  ответ клиента на запрос данных
POST   /applications/{id}/offer/accept

POST   /bank/applications/{id}/score     запуск скоринга
POST   /bank/applications/{id}/decision  одобрить / отказ / контрпредложение / запрос данных
POST   /bank/applications/{id}/sign      симуляция подписания
POST   /bank/applications/{id}/disburse  симуляция выдачи

GET    /applications/{id}/audit
GET    /notifications
POST   /notifications/{id}/read

GET    /mock/bki/{company_id}
GET    /mock/egrul/{inn}
GET    /mock/fns/{inn}
```

Контракт фиксируется в `openapi.yaml` до начала кодирования. Типы фронта генерируются через `openapi-typescript`.

## 14. Тестовые данные и аккаунты

| Аккаунт | Роль | Сценарий |
|---|---|---|
| `client.approve@demo.local` | CLIENT | Хорошая история, стабильная выручка → одобрение |
| `client.counter@demo.local` | CLIENT | Средний балл или сумма вне лимита → контрпредложение |
| `client.reject@demo.local` | CLIENT | Просрочка / высокий риск → отказ |
| `underwriter@demo.local` | UNDERWRITER | Очередь и решения |
| `admin@demo.local` | ADMIN | Справочники и аудит |

Пароль у всех одинаковый, указан в README (это демо, не прод). Компании: разные ИНН, отрасли, возраст, выручка, долговая нагрузка.

## 15. Риски и меры

| Риск | Вероятность | Мера |
|---|---|---|
| Не хватит времени на весь объём | Высокая | Жёсткий MVP, feature freeze в День 4 до 12:00 |
| Влад — бутылочное горлышко | Высокая | Никита помогает с фикстурами и моками, фронт работает на MSW |
| Расхождение фронта и бэка | Средняя | Контракт-first, генерация типов, интеграция каждый вечер |
| Деплой в последний момент | Средняя | Первый деплой в День 2 |
| Потеря данных после рестарта | Средняя | Postgres в volume, проверка в День 2 |
| «Застрявшая» заявка | Средняя | Явная state machine + тесты переходов |
| Соблазн сделать ИИ вместо ядра | Высокая | ИИ только после зелёного основного сценария |
| Неясность с новостной лентой | Низкая | Уточнить у организаторов, не строить наугад |
| Модель с закрытыми весами | Низкая | Только open weights, это проверяемо |

## 16. Правила разработки

- Одна интеграционная ветка `main`, короткоживущие ветки под задачи.
- PR с кратким описанием, ревью до 10 минут, без «идеального» кода.
- Коммиты маленькие и осмысленные (история коммитов оценивается).
- Никаких секретов в репозитории, только `.env.example`.
- Любая идея вне MVP — в `BACKLOG.md`.
- Не мержим сломанный `main`: перед мержем — локальный запуск.
- Время дороже архитектурной красоты, но слои не смешиваем.
